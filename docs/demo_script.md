## Q&A 預設問題與答案

### Q1：為什麼選 Gradio 不用 Flask？

> Gradio 開發速度極快（幾行程式碼就能做出可用介面），對資料分析類的 demo 非常適合。
> Flask 雖更靈活但開發成本高，本專題的互動需求 Gradio 已足夠。

### Q2：資料是真實的嗎？即時海況哪來的？

> **值勤資料**是模擬的，但機率模型參考真實海事經驗（外海大浪比例顯著高於港口、大浪天縮短時數）。
> **海象資料**來自**中央氣象署開放資料平臺**的浮標觀測（資料集 `M-A0064-001`，
> 彭佳嶼/花蓮外海/東沙島/鞍部四個浮標站）。我們用免費 API 金鑰抓取，依 Douglas 海況等級
> 把波高換算成平靜/輕浪/中浪/大浪。
> 誠實說明：**今天 demo 若沒設金鑰，跑的是季節性模擬備援**（系統會在 `data_source` 欄位標記
> `synthetic`），設了 `CWA_API_KEY` 就會變成真實的 `cwa_api` 資料——這是刻意設計的降級備援，
> 確保沒網路/沒金鑰也能完整 demo。

### Q2b：那「即時」體現在哪？

> 儀表板的海象橫幅、地圖浮標標記都讀 `sea_observations` 最新一筆觀測（最新 `obs_date`），
> 並驅動 scikit-learn 預測明日海況、進而調整排班員額。資料一更新，班表就跟著變。

### Q3：為什麼要用三個容器？

> 責任分離：PHP 處理使用者介面、MySQL 持久化、Python 做分析。
> 各容器可獨立擴充或替換，例如未來 PHP 換成 Next.js 不影響其他容器。

### Q4：船艦圖為何特別畫安平級？

> 「海事勤務」對應到台灣場景就是海巡署，安平級是現役主力 600 噸雙體巡防艦。
> 真實解剖學畫出來有專業感、辨識度高。整張圖純 SVG 約 50 行 PHP/SVG。

### Q5：MySQL 密碼怎麼處理？怎麼處理 GitHub 洩漏？

> 全部透過環境變數注入。`.env` 已加入 `.gitignore`，`db.php` 用 `getenv()` 讀取。
> 此外發現舊版本曾不小心 commit `.env.txt`，已用 `git-filter-repo` 改寫歷史並 force-push 清除。

### Q6：CSRF 怎麼實作？

> 自製輕量版：`csrf.php` 提供 `csrf_token / csrf_input / csrf_require` 三個函式。
> session 內存 token、每個 POST 表單帶 hidden input、handler 入口校驗、不符 403。
> 不引入任何第三方套件。

### Q7：分析圖表是 PNG 還是互動的？

> 統計圖表用 PNG（PHP 端免 JS runtime 即可嵌入、方便存報告）；
> 但**海域地圖是真正互動的 Folium HTML**（`duty_map.html`），以 iframe 嵌入儀表板，
> 可縮放、點擊海域看統計、看船艦與浮標 tooltip。兩種各取所長。

### Q10：你們和第 5 組（海象資料視覺化）到底差在哪？

> 一句話：**他們分析海象，我們用海象做人力決策。**
> 結構性差異在資料——他們只有海象觀測值；我們有人員打卡、勤務、船艦三種資料，
> 所以做得出疲勞指數、工時公平性（Gini/Lorenz）、船艦維護、以及最關鍵的
> **自動排班引擎（明日班表）**。這些純海象資料都做不出來。我們是決策支援系統，不是視覺化平台。

### Q11：排班引擎是怎麼運作的？是 AI 嗎？

> 它是**規則式決策引擎 + ML 預測輸入**的組合（`build_schedule()`）。
> ML（RandomForest）負責預測明日惡劣海況機率；引擎再依此機率決定外海員額，
> 並用「疲勞分數 × 0.6 + 外海暴露 × 0.4」對人員排序：外海優先給低分（低疲勞低暴露）者、
> 過勞者配港口、維護中船艦排除。沒有用黑箱大模型，邏輯完全可解釋、可向老師說明每個決策原因。

### Q8：Docker compose 啟動順序怎麼處理？

> `depends_on` 配合 `healthcheck`：web 和 analysis 容器會等 MySQL 健康後才啟動，
> 避免連線失敗。

### Q9：UI 為何選 RAL 7013 灰綠？

> 海事氛圍（軍規／北約色系常見）、可讀性高、配上 Claude 橘做行動色形成對比。
> 整套色票在 `style.css` 開頭一處定義，全站變數化。
